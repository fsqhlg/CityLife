# CityLife 项目面试追问手册（RocketMQ 版）

> 用法：不要背“功能列表”，按“问题 -> 方案 -> 为什么 -> 边界”回答。每个技术点先讲你解决的真实问题，再讲实现，最后主动说局限。

## 1. 秒杀主链路与 RocketMQ

### Q1：为什么把消息队列换成 RocketMQ，而不是继续用 Redis Stream？

Stream 版能解决“Lua 扣减 + 入队原子”，但它更像一个轻量消息队列：消费者组、pending、认领都要自己写，重试和死信也要自己维护。项目引入 RocketMQ 是为了把**削峰、失败重试、死信、消费扩容**交给成熟中间件，同时保留 Stream 作为本地 outbox。

最终链路是：

```text
Lua 原子扣库存 + XADD seckill:outbox + 写流水
        ↓ SeckillOutboxRelay
RocketMQ seckill-order-topic
        ↓ SeckillRocketMQConsumer
MySQL 订单 + 库存
```

Stream 不直接承担订单消费，只负责“扣减成功后，消息一定先落在本地”。RocketMQ 负责主消费。

### Q2：为什么不让 Lua 直接发 RocketMQ？

Lua 运行在 Redis 里，不能调用 Java 的 RocketMQ producer。如果拆成“Lua 扣减”然后“Java 发 MQ”，中间会有两个窗口：

1. Lua 成功、Java 发 MQ 前宕机：库存扣了，消息没发；
2. Java 发 MQ 成功、但本地事务回滚：消息发了，库存没扣。

项目用 Redis Stream 做 outbox，把“扣减”和“消息落本地”放进同一个 Lua，先消除第一个窗口；RocketMQ 消费端再用幂等和流水消除第二个窗口。

### Q3：outbox 转发失败怎么办？

`SeckillOutboxRelay` 用消费者组 `seckill-outbox-cg` 读 `seckill:outbox`：

- 发送 RocketMQ 成功才 `XACK`；
- 发送失败不 ACK，消息留在 pending；
- 空闲超过 60 秒由其他 relay 用 `XPENDING + XCLAIM` 认领重试；
- 超过最大重试次数写入 `seckill:outbox:dlq`，避免毒消息无限循环。

这样即使 RocketMQ 短暂不可用，消息也不会从 Redis 里消失，恢复后继续转发。

### Q4：RocketMQ 消费失败会怎样？

`SeckillRocketMQConsumer` 消费 `seckill-order-topic`：

- 正常建单返回 `SUCCESS`；
- 抛异常返回 `RECONSUME_LATER`，RocketMQ 按 `maxReconsumeTimes=3` 重试；
- 超过 3 次进入死信 Topic `%DLQ%seckill-order-consumer`；
- 消费端按 `orderId` 幂等，重试不会重复建单。

死信不是“自动恢复”，而是把毒消息隔离出来，后续靠人工/定时任务处理。

### Q5：消息重复消费会不会重复建单？

会重复投递，但不会重复建单。建单有四层幂等：

1. 先按 `orderId` 查订单，已存在直接返回成功；
2. 再按 `(userId, voucherId)` 查历史订单，已有其他订单拒绝建新单；
3. 数据库库存条件扣减 `WHERE stock > 0`；
4. 唯一索引 `uk_user_voucher(user_id, voucher_id)` 兜底，`DuplicateKeyException` 按成功处理。

### Q6：如果订单已经取消/回滚，RocketMQ 又投递了一条消息怎么办？

消费者在建单前会检查扣减流水：

- 流水状态是 `ROLLED_BACK` 或 `CANCELED`，直接跳过建单；
- 否则才走正常建单。

这是为了防止“库存已经回补、消息又到”导致重复占用库存。仅靠订单唯一索引不够，因为订单可能已经被取消，唯一索引仍然存在，但库存已经加回去了。

## 2. 一致性

### Q7：Redis 扣了库存，但数据库没落库，怎么办？

三层兜底：

1. **流水**：Lua 扣减时写 `seckill:ledger:{voucherId}`，状态 PENDING；
2. **消费者**：建单成功改 DONE；建单失败立即回滚库存并改 ROLLED_BACK；
3. **对账任务**：每分钟扫描 PENDING/FAILED 且超过 90 秒的流水：
   - DB 已有订单 -> 补 DONE；
   - DB 没订单 -> 重新投递 RocketMQ，不绕过 MQ 直接写 DB；
   - 重投超过上限 -> 回滚库存，改 ROLLED_BACK。

### Q8：为什么不用 RocketMQ 事务消息？

事务消息要求“本地事务执行”和“事务回查”，项目里本地事务是 MySQL 建单，而扣减发生在 Redis。真正要解决的是“Redis 扣减”和“消息发送”的原子性，RocketMQ 事务消息覆盖不了 Redis 这一步。

当前方案是“Redis Lua 本地 outbox + MQ 幂等消费 + 流水对账”，属于最终一致性。生产环境如果要把 outbox 换成 MySQL 本地消息表，可以再配合事务消息做更强的一致性问题。

### Q9：为什么不用 Seata？

这是单体项目，引入 Seata 成本高、面试也讲不完。这里用“本地事务 + 幂等 + 对账”的最终一致性方案：

- 建单是本地事务：扣 DB 库存 + 插订单，失败一起回滚；
- Redis 侧用 outbox 和流水记录中间状态；
- 对账任务是补偿器，负责把半成品收敛。

如果上生产，可以把对账任务换成事务消息/Kafka + 消费重试，但核心思路不变。

### Q10：取消订单为什么不能把用户从已购集合移除？

因为业务规则是“一人一单，取消后不允许复购”。

如果取消时 `SREM seckill:order:{voucherId}`，用户还能再抢一次；但数据库唯一索引会拦住第二次插入，出现“Redis 扣减成功、DB 没有订单”的假成功。

所以 `return_stock.lua` 加了 `keepQualification` 参数：

- 取消/超时：保留已购集合，只回补库存；
- 建单失败回滚：移除已购集合，允许用户重试。

### Q11：取消订单数据库库存要不要加回来？

要。否则 Redis 库存加回来了、DB 库存没加，两边越差越多，后面 DB 条件扣减会失败。

`returnStock` 在 Redis 回补成功（Lua 返回 1）后，执行：

```sql
UPDATE tb_seckill_voucher SET stock = stock + 1 WHERE voucher_id = ?
```

用 `seckill:returned` Set 保证同一订单只回补一次，所以 DB 也只加一次。

## 3. 订单状态机

### Q12：支付和取消同时发生，会不会都成功？

不会。两边都是条件 UPDATE：

```sql
UPDATE tb_voucher_order SET status = 2 WHERE id = ? AND status = 1;
```

```sql
UPDATE tb_voucher_order SET status = 4, close_type = 1 WHERE id = ? AND status = 1;
```

只有一个能更新成功，另一个返回 0 行，业务返回“状态已变更”。

### Q13：多实例部署，超时关单会不会重复？

不会重复关单，但可能重复扫描：

- 每个实例都可以扫 ZSet；
- 关单用条件 UPDATE，只有一个实例能成功；
- 库存回补用 `SADD seckill:returned` 幂等，只有一个实例真正 `INCR`。

所以多实例安全，代价是少量无效扫描。

### Q14：延迟队列为什么用 ZSet，不用 RocketMQ 延迟消息？

RocketMQ 4.9.8 的延迟消息只支持固定级别（1s/5s/10s/30s/1m...），不能精确到“订单 15 分钟后关闭”的任意时间。项目用 ZSet 存到期时间：

- `ZADD seckill:order:delay score=关闭时间 member=orderId`；
- 定时任务 `ZRANGEBYSCORE 0 now` 取到期订单；
- 支付/取消后 `ZREM`。

如果生产环境用 RocketMQ 5.x 的定时消息，可以替换 ZSet 扫描。

## 4. 缓存

### Q15：布隆过滤器误判怎么办？

布隆只能“判断一定不存在”，不能“判断一定存在”。

- 返回“不存在”：一定不存在，直接拒绝；
- 返回“可能存在”：继续查缓存/DB，由空值缓存兜底。

项目里如果 `bloom:shop` 被清空，`mightContain` 会 fail-open 返回 true，宁可多查一次 DB，也不能把所有请求判死。

### Q16：互斥锁为什么要用 UUID + Lua 释放？

经典问题：

1. 线程 A 加锁，TTL 10 秒；
2. A 业务阻塞超过 10 秒，锁自动过期；
3. 线程 B 加锁成功；
4. A 醒来执行 `DEL`，把 B 的锁删了。

解决：

- 加锁时 value 存 UUID；
- 释放时 Lua 比较 value，相等才 `DEL`。

### Q17：缓存穿透、击穿、雪崩分别怎么处理？

- 穿透：布隆过滤器 + 空值缓存（TTL 2 分钟）；
- 击穿：互斥锁（默认）或逻辑过期（热点 key 预热）；
- 雪崩：TTL 加 0~9 分钟随机值，避免同一时刻大量 key 过期。

## 5. 限流与登录

### Q18：为什么用滑动窗口，不用固定窗口？

固定窗口有临界问题：窗口边界前后各打满，实际 2 秒内可以通过 2 倍限额。

滑动窗口 Lua：

1. `ZREMRANGEBYSCORE` 删除窗口外请求；
2. `ZCARD` 统计窗口内数量；
3. 未超限则 `ZADD` 当前请求，`PEXPIRE` 设置过期。

时间用 Redis `TIME`，避免多实例时钟漂移。

### Q19：验证码和登录怎么防刷？

- 验证码 IP 维度 5 次/小时；
- 同一手机号 60 秒 1 次；
- 登录失败 15 分钟内 5 次锁定；
- 登录成功清空失败计数；
- 验证码一次性使用，比对成功立即删除。

## 6. 压测与边界

### Q20：压测结果多少？

本地单机、库存 100、200 个不同用户、线程栅栏同时请求：

- 100 成功、100 库存不足；
- 0 重复、0 其他异常；
- DB 订单 100、DB 去重用户 100、DB 库存 0；
- Redis 库存 0、已购集合 100、流水 100；
- outbox pending 0；
- 请求端到端约 574ms，约 348 req/s。

这不是生产 QPS，只是证明“不超卖、不重复、消息全部消费”。真正上生产要压集群、调 Tomcat/连接池、加 RocketMQ 多队列和消费实例。

### Q21：瓶颈在哪里？

当前单机瓶颈主要在：

1. Redis 单线程执行 Lua；
2. outbox relay 单线程转发；
3. RocketMQ 单 Master、4 队列；
4. 消费者落库是串行 DB 事务；
5. Tomcat 线程池和 Lettuce 连接池；
6. Windows 本机文件/网络开销。

优化方向：

- outbox relay 多线程/多实例；
- RocketMQ 增加队列和消费者实例；
- 消费者批量建单、批量 ACK；
- 数据库分库分表/批量插入；
- Redis Cluster。

### Q22：这个项目最大的难点是什么？

“Redis 和 DB 最终一致”不是靠一个注解解决的：

- 要保证扣减和消息落本地原子；
- 要保证 outbox 转发不丢、可重试；
- 要保证 RocketMQ 消费不丢、可重试、有死信；
- 要保证建单幂等；
- 要能发现并补偿半成品；
- 还要保证取消/超时回补只执行一次。

我的做法是“Lua 原子入口 + Redis outbox + RocketMQ 可靠消费 + 流水对账 + 唯一索引兜底”，每一层只解决一个问题，出问题能定位到哪一层。

## 7. 30 秒项目介绍模板

“CityLife 是一个本地生活服务项目，基于黑马点评二次开发。我没有堆中间件，而是把秒杀链路补完整：Lua 内原子扣库存并写 Redis outbox，`SeckillOutboxRelay` 把消息转发到 RocketMQ，消费者按 orderId 幂等建单，失败重试 3 次进死信；订单状态机和 ZSet 延迟队列做支付/取消/超时关单，扣减流水 + 定时对账解决 Redis 和 DB 的最终一致，唯一索引兜底一人一单。压测 200 并发、库存 100，做到 100 成功、100 售罄、0 超卖、0 重复，outbox pending 为 0。”

## 8. 不要主动说的坑

- 不要说“QPS 348 很高”，主动说这是本地单机验证；
- 不要说“完全解决了分布式事务”，说“最终一致性 + 对账补偿”；
- 不要说“RocketMQ 一定比 Stream 好”，说“Stream 做本地 outbox，RocketMQ 做主消费，各司其职”；
- 不要背“RocketMQ 底层源码”，除非面试官追问，先说 outbox、重试、死信、幂等四条；
- 不要隐瞒 outbox 的存在，否则会被追问“Lua 怎么发 MQ”时答不上来。
